# 阶段同步流程

本文件描述把本地改动同步到 GitHub 独立仓库的标准阶段流程。流程的目标是：**每次推送前都在本地完成同样的检查**，并且推送只能是显式动作。

所有命令都在仓库根目录执行，路径一律使用仓库相对路径。

## 六步流程

1. **检查目标仓库和变更**：确认工作树根就是源码仓库、所有远程都指向本项目独立仓库、分支正确，并列出本次改动文件。
2. **相关测试与生产配置检查**：按改动范围选择要跑的 Node 测试；小程序生产边界检查每次都跑（含 AppID、分包、分享入口、皮肤契约）。
3. **检查暂存内容与密钥排除**：逐行扫描暂存的新增行，拦截私钥、令牌、AppSecret 等凭据形态；同时拦截 `.env`、`*.pem`、`*.key`、`*.p12`、`id_rsa`、`project.private.config.json` 等敏感文件名。
4. **按真实 Git 身份提交**：提交只读取仓库/全局配置里的 `user.name` 与 `user.email`，不传 `--author`、不写死作者；没有配置身份时直接失败。
5. **显式手动推送**：默认只做预检/dry-run，真正推送必须显式加 `--execute`。
6. **核对远程提交**：抓取远程分支并逐项比对本地 HEAD、远程引用与 `ls-remote` 结果。

```sh
# 1–3 只检查，不提交、不推送
node scripts/ci-stage-sync.js check

# 4 本地提交（默认把所有未忽略改动加入暂存；--no-add 则只提交当前索引）
node scripts/ci-stage-sync.js commit --message "<本次改动的主题>"

# 5 默认 dry-run：不写远程
node scripts/ci-stage-sync.js push

# 5 显式真正推送，并自动执行第 6 步
node scripts/ci-stage-sync.js push --execute

# 6 单独核对远程提交（只读）
node scripts/ci-stage-sync.js verify
```

常用参数：`--base <sha>` 指定比较基线（默认 `origin/main`，取不到时用上一个提交），`--full` 强制全量检查，`--skip-tests` 跳过测试（仅用于只想看仓库与暂存状态的场合），`--report <仓库内路径>` 指定检查报告输出位置（默认 `outputs/stage-sync-report.json`，已被 `.gitignore` 忽略）。

报告只写项目目录内；传入项目外的路径会直接失败。

## GitHub 检查与微信上传的触发关系

- 两个工作流都只声明 `workflow_dispatch`，**代码推送不会触发任何工作流**，因此也不会触发微信上传。
- 阶段同步脚本会把“所有工作流都只能手动触发”作为硬校验；一旦有工作流加入 `push`、`schedule` 等自动触发，检查立即失败。
- 手动上传工作流额外要求：版本号等于 `package.json`、说明非空且不超过 200 字符、确认字段精确填写 `UPLOAD`、当前引用为 `refs/heads/main`，且该提交已通过成功的检查门禁。
- 不默认创建 PR，不推送标签，不强推，不导入旧历史。

## 微信上传是独立流程

阶段同步**不调用任何微信上传、提审或发布命令，也不读取上传密钥、不修改 AppID**。微信上传只在用户明确指定时，通过独立的手动工作流或本地发布脚本进行。

同一份代码、同一个 AppID 在不同仓库或不同 CI 机器人下**不等于两个独立小程序**：

- 未来若使用同一 AppID 与同一上传身份，开发版可能被互相覆盖。
- 共用后端意味着数据也可能共享。
- CI 机器人分开也不代表正式版隔离。

因此每次上传前必须逐项核对：**源码路径、AppID、版本号、目标环境、上传身份**。在用户另行指定测试小程序或发布安排之前，只做本地验证。

## 边界与缓存

- 所有输出、临时文件与可配置缓存都留在项目目录内。
- 脚本会把 `npm_config_cache` 与 `TMPDIR` 收敛到项目内目录（用户显式指向项目内的取值才沿用）。
- 第三方 `LICENSE`、`NOTICE` 与来源说明随代码保留，不得删除或改写归属信息。
