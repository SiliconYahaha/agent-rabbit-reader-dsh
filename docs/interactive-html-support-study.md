# 复杂交互 HTML 的微信支持调查


## 实现进展（更新）

采用共用浏览器兼容层，不修改或按文件名特判私人原件。下方初始调查保留为问题来源，以下状态优先。

- SVG：增加 viewBox/坐标变换、基本图形命中与多指捕获；实际微信 WXML 图片的开始点击和双指按住/释放已通过。尚未实现任意 SVG 路径、笔画与裁剪的完整浏览器命中语义。
- Canvas：补 replaceWith，独立动画调度不再累计消耗普通定时器的 240 次额度，保留每帧保护、后台暂停与关闭清理；原生 2D 画面不再累计重放绘图命令。51 个内嵌图像加载成功，实际 WXML 开始操作和超过 60 秒主画面/小地图修订持续更新通过，备用绘制路径不再报像素超限。音频、全部技能、物理手机和整页合成画面尚未完整验收。
- WebGL：正确创建 WebGL2，保留真实扩展和查询对象，缺少原生能力时返回 null；像素在本机画布桥中传递，不进入 setData。加入缓冲保留和上下翻转读回路径，实际 WXML 画布彩色像素已验证，整页合成画面仍待验证。
- 样式尺寸：脚本读取样式表的高度与视口单位，不再把全屏容器高度当作 0。
- Three.js：仅对 SHA-256 与全部 419 个导出完全匹配的官方 r169 库使用预编译包；官方 npm 压缩包完整性、源码摘要与 MIT 许可证随模块记录。用户逻辑仍经过隔离解释器与执行保护，修改过的库不会获得该路径。
- 经用户明确授权：原生画布池上限为 64M 像素（约 256 MiB RGBA，仅画布池，不代表进程或 GPU 总内存上限），关闭文件释放画布；已识别的 Three.js 初始化最多 200 万受控步骤、单个同步任务最多 2 秒，第一动画帧恢复 5 万步保护。

3D 原件已在微信完成初始化、实际 WXML 开始点击和油门按住/释放，车速上升，随后连续 30 秒没有脚本错误。对已识别官方 Three.js 的宿主主动点击，沿用用户授权的 200 万步骤 / 2 秒同步任务保护；脚本合成点击和动画仍保持 5 万步。该时间保护是合作式检查，不能中途抢占单次原生库调用。

补齐触屏媒体条件（pointer/coarse、hover/none），让 HTML 自己的移动摇杆样式生效。已在实际 WXML 验证摇杆按下、拖动后位移变化与松手回中。原生事件缺少 changedTouches 时，按活动手指编号恢复按下、移动与释放，避免双指互相干扰。脚本替换 Canvas 时，丢弃异步查询尚未完成的旧帧；仍存在的画布缺少原生资源继续报错。

画布验证：重启开发者工具后，实际 WXML Canvas 2D 可读取彩色图像；2D 样本多次有超过 190 种抽样颜色，3D 样本超过 1,300 种。开发者工具整页截图仍不能作为完整视觉通过证据：画布能被捕获，但普通 WXML 操作层未出现在合成图中；对应 WXML 控件的尺寸、显示样式与事件可读取。原生窗口检查接口超时，尚未确认是截图合成问题还是设备上的层级问题。未验证物理手机、完整操作层、音效或长时间手机性能，不宣称任意 HTML 或三份游戏完整可玩。

针对性检查：本轮补充的图形、触控与预算 35 项通过，触屏条件和相关排版 23 项通过（存在重叠）。此前脚本/隔离、资源预算、样式尺寸、图形展示与原生预算合计 91 项通过；随后新增 GPU 像素翻转/复用检查，相关 31 项通过（与前组有重叠）。未执行不相关格式的全套测试或重新触发 GitHub Actions。

复测入口：`scripts/verify-interactive-games-wechat.js <本地原件目录>`、`scripts/verify-webgl-game-wechat.js <本地原件目录>`。后者的 `--garage` 仅检查启动与可见像素，不代表比赛操作通过。报告放在忽略的 `outputs/hard-html/`。

## 结论

三份原件均能在本机 Chrome 中进入游戏。现有小程序读取器用隔离解释器和小程序视图模拟浏览器的一部分能力，并不是完整浏览器。仅提高文件大小限制不能让这些游戏正常运行。

建议保留本地文档阅读，针对复杂游戏评估单独的完整网页模式。若坚持离线、文件不离开设备，则先完成 SVG/Canvas 2D 的输入与持续绘制支持；Three.js 游戏需要独立移植或更完整的图形宿主，不应承诺任意 HTML 直接可玩。

## 共同限制

- 运行器每份文档最多触发 240 次定时回调，用户操作只补回少量额度。持续动画需要独立调度设计，保留每帧执行预算、后台暂停、关闭清理和异常停止；不能简单取消限制。
- SVG 图片保留视觉但没有 SVG 子元素原生事件目标。直接在测试中调用子节点 `dispatchTap` 会绕过真实输入问题。
- 宿主支持时存在真实离屏 WebGL 桥；宿主不支持时现有假 WebGL 只记录命令、返回全零像素，会误导能力探测。真实桥还把查询对象包成资源句柄，没有完整区分扩展对象、参数对象、纹理图片和上下文版本。需要单独修正并验证，不能把提供 `getContext` 等同于实现完整 WebGL。
- 现有 WebGL 画面会逐帧回读像素，再经视图通道展示。1280×720 的一帧 RGBA 原始数据已是 3,686,400 字节，尚未计 JSON 开销；实时游戏应研究直接绘制到可见原生 Canvas。
- 游戏使用 Web Audio；现有普通媒体播放并不等于支持游戏混音、解码和低延迟音效。还要验证用户首次点击启音、暂停恢复和切换文件释放资源。

## 在微信中的两条路线

### A. 完整网页运行模式：适合任意复杂 HTML

用真正的 H5 浏览器运行页面。小程序内可评估 `web-view`，前提是主体具备权限、配置业务域名，并有 HTTPS 页面来源。腾讯 CloudBase 文档明确说明该组件在小程序端需要企业账号和业务域名；当前项目主体资格尚未确认，不能默认可用。[腾讯 CloudBase 文档](https://docs.cloudbase.net/en/lowcode/components/wedaUI/src/docs/compsdocs/super/WebView)

建议的具体原型：主界面保留“本地阅读”，另设“完整网页模式”；先用自建非私人小游戏验证 SVG 点击、2D 绘制、3D 着色器、音频启用及横竖屏，再接入明确同意后的文件流程。网页内容使用独立无登录凭据的运行域名、短期不可猜测地址和自动清理；输入文件不应在主业务域名直接执行。具体隔离、浏览器限制及微信内核兼容仍需原型验证。

当前生产配置明确禁止上传与远端网页，这条路线会改变“文件仅在本机处理”的产品承诺。现有 `server/` 只是保留实验，不能直接启用为上线方案。本轮没有部署服务或上传私人文件。如果主体不支持 `web-view`，只能另评估微信内打开的 H5 链接等入口，不能声称仍然内置在当前小程序。

### B. 本地适配：适合有限、明确支持的交互类别

优先做 SVG 输入和 Canvas 2D，并采用真实宿主直接绘制。对 Three.js 作品按游戏单独移植。微信官方提供绑定到小程序 Canvas 的 Three.js 适配方案，但 README 标示版本为 0.108.0，不能直接替代任意 HTML 中内嵌的 Three.js。[微信官方适配仓库](https://github.com/wechat-miniprogram/threejs-miniprogram)

实施顺序建议：

1. 先完成 SVG 游戏的点击、长按、多指和暂停恢复；验证真实视图命中，不能只调运行器事件。
2. 修正 Canvas 能力检测和 DOM 缺口，选择可见 Canvas 直接绘制；再测 2D 游戏资源加载和连续交互。
3. 3D 使用专门的适配试验，不把 20 万节点脚本直接放进当前文档运行器，也不宣称一套 shim 可以完整覆盖浏览器。

每阶段验收仅跑受影响范围：打开 → 开始 → 操作 → 连续运行至少 60 秒 → 后台/恢复 → 切换文件清理。正式声称支持前至少覆盖一台 iOS 和一台 Android 微信；确认画面在变、输入有效、无持续内存增长，不能以静态首页截图验收。
