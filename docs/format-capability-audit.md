# 文件格式内容能力审计

本项目把“识别出文件类型”和“用户真正看到内容”分开验收。机器可读清单位于 `miniprogram/file-reader/shared/format-capabilities.js`，自动化会确保v1.4.146代码 `file-types.js` 声明的 74 个扩展名全部登记内容等级、可见结果、验收证据和限制。新增 XHTML/XHT 仍待微信实际验证，不等于线上已支持。

## 结论

74 个扩展名包含别名、源码阅读、条件预览和微信原生查看，并不代表全部完整还原：

| 内容等级 | 扩展名数量 | 含义 |
| --- | ---: | --- |
| 完整内容 | 27 | 小程序直接显示正文或画面 |
| 微信原生内容 | 14 | 交给微信文档或图片查看器显示内容 |
| 条件内容 | 28 | 取决于文件内部数据、编码、平台或解压条件；满足条件时显示真实内容 |
| 部分真实内容 | 4 | 只还原有确定证据的图元、曲面或对象，不冒充完整编辑器 |
| 内容未支持 | 1 | 只能检查文件身份，不能把结果称为内容预览 |

目前唯一明确属于“内容未支持”的扩展名是 **DWG**。它只能显示保存版本，文件自身偶尔带有 JPEG/PNG 时只能称为“内嵌缩略图”，不能称为图纸预览。

## 此前没有考虑好的地方

1. **把文件头识别当成内容支持。** DWG 最明显：版本号和缩略图都不是图纸。现在只有真实正文、画面、声音、目录或模型才算内容证据。
2. **用一个布尔值混淆不同结果。** 旧 `contentReady: false` 同时覆盖了“压缩包能打开条目”“媒体受平台限制”“工程文件只支持部分几何”和“DWG 完全没有图纸”，无法指导验收。现在改用五级内容分类。
3. **没有把条件说到用户能行动。** 现在压缩包说明密码、分卷和大小边界；音视频说明平台；Ai/PSD/CDR 说明必须依赖哪类内嵌数据；DWG 给出另存为 DXF 的路径。
4. **入口文案把所有工程文件说成同一能力。** 首页现在只明确列出 DXF、STEP、CDR 的已支持内容，并直接说明 DWG 暂不能看图纸。
5. **专有格式不能用“尽量还原”掩盖缺口。** Ai、PSD/PSB、CDR 只展示文件里真实存在、且有确定性样本验证的内容；没有证据时拒绝生成看似正常但实际错误的画面。

## 后续验收规则

- RTF 验收检查实际正文而非文件头：原始/hex/混合字节、字体代码页与 Unicode 回退均有独立对照或规范用例；嵌入二进制不参与正文分组。脚注/尾注与正文引用可双向跳转；完整分页、富文本布局、嵌图、符号字体及额外代码页仍为独立缺口，见 [RTF 档案](../compatibility/profiles/rtf.json)。
- 新增扩展名必须同时登记内容等级、用户可见结果、验收证据和限制，否则测试失败。
- `unsupported-content` 不能出现在“可看图纸/正文/画面”的宣传文案里。
- 条件内容必须至少有成功样本和失败/缺条件样本；失败时要告诉用户缺什么，不能显示空白页。
- 压缩包必须看到目录并能打开受支持条目；媒体必须出现真实播放器状态；设计/工程文件必须出现真实画面或模型，不能只显示元数据。
- 压缩包目录中的文件名也是内容。普通 ZIP 没有 EFS/Unicode Path 时保留自动模式（合法 UTF-8，否则 CP437），但必须明确标注自动判断并允许改为 UTF-8、CP437、GBK、Shift_JIS、CP949/EUC-KR 或 Big5；手动选择不能再次被自动判断覆盖。韩文编码同时覆盖 EUC-KR 常用区和 Windows UHC 扩展区；兼容内核接管后也按中央目录原始字节覆盖显示名，并按原生成员序号提取正文。0x7075 Unicode Path重复或extra字段截断时不得按出现顺序猜名称，必须回退中央目录原始名称，同时保留安全正文读取。
- 7-Zip 技术清单中的空行是条目分隔符，不得当日志噪声删除；目录验收必须覆盖多文件、空文件及固实归档，并逐条对比解压正文，不能只验证最后一个条目。
- 7-Zip 清单只识别独立分隔行；连续横线和首尾空格属于文件名数据，不能截断目录或改名。扩展名判定允许尾部空白，但原读取路径和解压字节保持不变；验收覆盖 ZIP、固实 7z、数字分卷和微信页面真实点击。
- 7z 在 Unix/WASM 下的字面反斜杠属于文件名，不是目录分隔符。普通、加密文件头、同名成员及数字分卷均按原生名称开启正文；Windows 盘符、UNC 和反斜杠目录越界仍当作不安全路径拒绝。
- 7z 固实压缩不能只看压缩包大小或目标成员大小。目录根据原生 `Packed Size` 的块起点累计目标成员之前必须解码的数据；恰好80MB允许，超过1字节即保留成员信息并禁用打开，新固实块重新计数。该值是解码工作量边界，不等同于精确峰值内存。
- 本清单描述的是当前真实能力，不代表完整替代 Illustrator、Photoshop、CorelDRAW 或 CAD 软件。
- 解压器标准输出中的文件名、注释不是错误状态；命令失败依据退出状态与异常，诊断来自独立错误流。回归同时覆盖正常错误关键词名称与真实 CRC 损坏，禁止为消除误报而放行损坏内容。
- 点选压缩包成员是精确文件选择，不是命令行通配符表达式；星号、问号、@ 和 - 等属于名称。必须检查解压清理前的全部实际输出，避免隐藏未选中大文件或损坏成员被额外解压；固实块解码成本另行评估。
- 同名成员不能合并成一个条目，也不能只按名称提取最后一份正文。先按最终显示路径规范化斜线并标记同名序号，再用不可见的原始成员身份提取；不同原始编码字节解码成同一 Unicode 名称时同样如此。ZIP 按中央目录序号和本地头位置、RAR 按头部序号、7-Zip 按原生同名次序选择，再校验大小和 CRC；绝对路径保留完整警告且不可点击，不能去掉前导斜线后冒充安全文件。回归包括缺密码后换包、空文件、未选中损坏成员、旧编码同名和规范化路径同名。
- ZIP 的 Unix 符号链接不能作为普通文本打开。只在中央目录明确声明 Unix 链接时读取不超过4096 B的 UTF-8目标，在包内按相对路径和中央目录成员身份解析；支持文件夹与中间目录链接，拒绝绝对路径、越界、循环、缺失、隐藏系统项和重名歧义。普通 Store/Deflate 直接读取；BZip2、AES 等兼容内核场景只在隔离内存副本中把链接记录当普通数据解码，不创建宿主链接、不修改原 ZIP，重复打开仍返回同一正文。解析使用完整中央目录，不受500项界面显示上限影响；不受支持的方法只禁用对应成员。ZIP64 单包、`.zip.001/.002/.003` 数字分卷、普通及ZIP64 `.z01/.z02/.zip` 经典分卷均已按真实中央目录验证包内链接；ZIP64经典分卷叠加旧文件名编码仍是独立缺口。
- v1.4.43 修复公开 RAR 样本中的符号链接 testlink：显示目标名称并在包内解析到真实 HTML 正文，20111 B 结果与 bsdtar 一致。RAR5 普通符号链接、硬链接和文件夹链接另有独立样本；目录可返回，空目录有提示。后续已分别验证路径中间链接、RAR4 旧式非 UTF-8 目标、RAR5 加密文件头内的符号链接、正文跨越两个真实 RAR5 分卷时的链接，以及加密文件头与分卷链接同时出现的组合：未输入密码和错误密码均拒绝，正确密码解锁后按成员序号提取跨卷真实目标；缺卷、越界、循环、缺失和重名仍拒绝。iOS/Android 真机内存边界继续独立排队，不推断为全部链接已支持。
